# The type merge programme: one implementation per mechanic (DESIGN §22)

**Ruling (maintainer 2026-09-30):** every mechanic has ONE implementation. Where OpenRA, RV/AS, CA, Cameo, Cnc, D2k,
Fransbot — or a reference mod Cameo never copied from — carry variants of the same trait, projectile, warhead or
bot module, the best features of all of them are merged into one type, every user is switched to it, and the new
features are then put to use. The law and the per-family pipeline are DESIGN §22; this file is the programme:
measured scope, order, estimate and risks.

**Inventory:** [`TYPE_MERGE_INVENTORY.md`](TYPE_MERGE_INVENTORY.md), generated by
`python tools/audit/type_merge_inventory.py` (re-run it; never edit the file). It scans the 7 loaded assemblies and
4 reference mods (upstream CA, Shattered Paradise, Generals Alpha, Romanov's Vengeance).

BevManager ↔ McvExpansionManager, the engineer modules). Expect both the family count and the tiers to move once
each family is read.

## 2. Who owns which families

* **Bot-layer families (17, ~258 h):** the `…BotModule` families including the Fransbot donors, plus `ModularBot` and
  `GrantConditionOnBotOwner`. The AI plan owns them —
  `AI_MASTER_PLAN.md` §3 (RV1 done, RV2 support powers, ENG engineers, BEV, and the FB/CN harvest items), under
  DESIGN §19.3. The Fransbot "co-live" rows are the donor stack (`fransbot` bot type only), merged as each module is
  harvested; `classic` keeps only the CA copy where a duplicate exists.
* **Everything else** (traits, projectiles, warheads): this programme.

## 4. Estimate

Three-point per tier (hours per family), as in `BALANCE_PIPELINE_ESTIMATE.md`:

| tier | families | O / M / P per family | expected per family | expected total |
|---|--:|---|--:|--:|
| identical / shadow | 21 | 0.5 / 1 / 2 | 1.1 | 23 h |
| small | 71 | 2 / 3 / 6 | 3.3 | 237 h |
| medium | 18 | 6 / 10 / 20 | 11 | 198 h |
| large | 9 | 15 / 30 / 60 | 32.5 | 293 h |
| **families** | **119** | | | **~750 h** (range ~400 … 1,370 h) |

Of the ~750 h, the 17 bot-layer families are ~258 h and belong to the AI plan (§2; RV1, RV2, ENG, BEV and the
harvest items already carry part of it). **This programme's own total: ~660 agent-hours** (M0 tooling 40 h + 102
families 492 h + M4 feature adoption ~125 h), **about 130 sessions**; range roughly 350 … 1,200 h (M0 25–70, families 270–894, M4 60–250).
Every family ends with a boot gate and a resolved diff, so the programme can stop after any family.

## 5. Risks and guards

| Risk | Guard |
|---|---|
| A conversion changes behaviour through a default nobody wrote | step 4 of DESIGN §22: old defaults written explicitly; `review_resolve_diff.py` must show no change for a no-op conversion |
| A field the merged type drops is silently ignored (the engine drops unknown yaml fields) | the merged type keeps every field of every variant; `audit_dead_warhead_fields.py` (warheads), and extend the same check to traits/projectiles in M0 |
| A shadow does not win (AS precedes Cameo in `Assemblies`) | prove every shadow with a Cameo-only field (rule 7); AS-named families take a new name + conversion |
| An upstream fix never reaches the merged type | `audit_merged_bot_modules.py` (parent hashes) for every merged type |
| A merge breaks a map that places an actor | `audit_map_actors.py` after every rename batch (rule 8h) |
| Balance moves by accident | rule 3: numbers only through the pipeline; M4 content changes are separate PRs |
